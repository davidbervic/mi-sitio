Waterfall Enrichment: What It Is and When to Use It (Clay vs Apollo vs ZoomInfo)

M Muvap Published Oct 14, 2026 Updated Oct 8, 2026 10 min read

Direct answer: Waterfall enrichment queries several data providers in a defined order for the same field and stops once a valid result is found or the sequence ends. Use it when one provider's miss rate on your actual list is the problem. If one provider already clears roughly 80% on an easy list, a waterfall adds cost and complexity for a few points. Most statistics cited here are vendor-reported and are labelled that way.

Key takeaways
  • A waterfall raises coverage only: Freshness, deliverability and correctness still depend on each provider's data and on your validation step.
  • Control model is the decision axis: Clay lets you own order and stop rules, Apollo uses an admin lineup with its own data first, and ZoomInfo manages order for you.
  • Test your miss rate first: Run one sample through one provider, split it by segment, and add providers only where misses are the problem.
  • Verify billing on misses: Sources conflict on whether failed lookups are charged, so test a small batch before budgeting.

What is waterfall enrichment and why is one provider not enough?

A waterfall runs the same field lookup through several providers in a set order and stops at the first valid result, because no single provider covers a full B2B list.

In single-provider enrichment, one vendor's database answers the lookup and a miss stays a miss. In a waterfall, a miss passes to the next provider, and a validation step can check the result before the sequence stops (Clay Docs).

Published coverage figures, all vendor-run or vendor-aggregated:

  • Single provider: FullEnrich, Landbase, QuickEnrich and Unify GTM publish figures from 30% to 70% (Landbase, Yalc, Databar).
  • Waterfall: the same sources report 80%+ or high eighties.
  • Clay's benchmark: per Databar's summary, no single provider cleared both 95% quality and 90% coverage, while a chain reached 94% usable coverage (Databar).

The evidence supports the direction (more coverage), not any specific lift. Coverage also varies by region, which is why one provider can look fine on US data and weak elsewhere (Yalc).

How do Clay, Apollo and ZoomInfo each run a waterfall?

Clay lets you build and order the sequence, Apollo gives admins a default lineup with its own data first, and ZoomInfo fills gaps in parallel without exposing provider order.

The deciding question is who owns provider order and stop rules, because that determines maintenance work, cost visibility and how far you can tune for one segment. Two claims still circulating in comparison pages are out of date. Apollo does have a waterfall: its December 2025 release notes show it, so pages saying otherwise are outdated or wrong (Apollo release notes). And ZoomInfo is not simply single-source: per ZoomInfo, it queries its own database first, then fills gaps from third-party vendors in parallel (ZoomInfo Pipeline).

Clay
You control order

Pre-built waterfalls for work email and phone can be reordered, extended, trimmed or toggled per provider, and custom waterfalls can be saved as templates. If a provider finds a valid email, the process stops for that contact; otherwise Clay moves to the next provider (Clay Docs).

Apollo
Admin controls the lineup, Apollo stays first

Waterfall became the default for finding emails and phones in December 2025. An admin sets a global lineup with an optional validator, can remove third-party sources entirely, and users can switch the waterfall off per activity. Apollo always stays first and cannot be moved (Apollo docs).

ZoomInfo
ZoomInfo controls order

GTM Studio Waterfall Enrichment was announced on 19 February 2026. Per ZoomInfo, it fills missing email or mobile data from third-party vendors in parallel, returns the highest-confidence result through Intelligent Scoring, and attributes a source to each data point (ZoomInfo press release).

How do Clay, Apollo and ZoomInfo compare on control, ordering and billing?

Clay gives the most control and the most configuration work, Apollo a managed default with a fixed native-first order, and ZoomInfo the least visibility into order and scoring.

Billing is where the control models diverge most. Clay runs two meters: every enrichment consumes one Action plus variable Data Credits, and a fully enriched record typically costs 6 to 20 Data Credits (Clay Docs). Misses are the contested cell: Clay's FAQ says no-result steps are free, while community threads and third-party write-ups claim per-attempt charges (Cleanlist).

Should a waterfall run sequentially or in parallel, and how many providers do you need?

Sequential first-match favours cost and control, while parallel scoring favours confidence per field and less order maintenance but is less transparent. Practitioners suggest starting with 2–3 providers.

ZoomInfo describes sequential waterfalls as slower and subject to first-match limitations, and parallel scoring as faster and free of double payment (ZoomInfo Pipeline). That is an argument for its own architecture. Clay and Apollo both run top to bottom, with Apollo's own data fixed first.

Sequential first-match
More control, visible spend

Each step runs only if the previous one missed. You see the logic and the spend, and you maintain the order. Used by Clay and Apollo.

Parallel scored
Less maintenance, less transparency

Vendors are queried together and the highest-confidence result wins. There is no order to maintain, but provider order and scoring logic are not exposed. Used by ZoomInfo GTM Studio.

On count: Landbase suggests starting with 2–3 providers and adding more only for a measurable gain (Landbase). Unify GTM's analysis, via Yalc, puts the practical optimum at 3–4: the second provider recovers roughly 15–25% of the first one's misses, the third 8–12% and the fourth 3–5% (Yalc). Read those as practitioner heuristics, not a proven curve.

Our rule of thumb for order: put the most accurate or most relevant source for the target geography first; put cheap steps before slow or expensive ones, with AI research last (Landbase); treat the default order as a starting point and reorder from test-batch results.

When is a waterfall worth it and when is one provider enough?

Use a waterfall when one provider's miss rate on your list is the bottleneck, typically outside US, tech and enterprise segments; about 80% from one provider is often enough.

An easy list (US tech, large companies, recent LinkedIn activity) that one source already clears at about 80% gains only a few points from a second provider, at real cost (Databar). Landbase says a narrow, well-covered ICP can see 70%+ from one provider, with a waterfall adding about 10–15 points plus complexity (Landbase). Fields that do not change routing, action, prioritisation or reporting are not worth enriching at all (Talantir).

Decision sequence before building:

  1. Does the field change routing, action, prioritisation or reporting? If not, skip enrichment for it.
  2. What is the miss rate for one provider on a representative sample? If it already clears roughly 80% on an easy list and the misses do not hurt, stay with one provider.
  3. Where do the misses cluster? Split by US vs non-US, company size and role.
  4. Choose the build. Clustered misses call for a targeted waterfall that adds providers only for those segments. Misses spread across the list call for a full waterfall, starting with 2–3 providers.

What should you define and measure before building a waterfall?

Define the target field, a validated-result stop rule, a validation step and a test batch; then measure lift per provider, cost per valid record and bounce rate.

A waterfall has three cost layers: data credits, orchestration Actions or platform meters, and RevOps time to keep provider order and rules current. Clay does not list per-provider credit costs on its pricing page; they appear in-app, so cost per record must be measured on your own recipe. Cleanlist's conversion of Clay's 6–20 credit range to about $0.30–$1.00 per fully enriched contact in Data Credits, plus Actions, is a third-party estimate, not a Clay figure (Cleanlist). Sources also conflict on billing for misses, so the test batch is both a quality gate and a billing check.

Pre-build checklist:

  • ☐ Pick one target field and confirm it changes routing, action, prioritisation or reporting
  • ☐ Write the stop rule: stop on a validated result, never on any non-empty value
  • ☐ Add a validation step after the providers and decide what happens to results that fail it
  • ☐ Set provider order by geography fit, with slow or expensive steps last
  • ☐ Run a small test batch before scaling and record whether misses consume credits or Actions
  • ☐ Gate CRM write-back so weak or unvalidated data never overwrites existing values

Measure the payoff with three numbers: (1) Coverage lift per provider — the share of previously missed records each provider recovers. (2) Cost per valid record — credits, Actions and maintenance time divided by validated results, not by non-empty results. (3) Bounce rate — bounces on validated emails actually sent. Log one row per provider in run order: records tried, valid results, credits or Actions consumed, and bounces from the first send.

What does a waterfall not fix?

A waterfall raises coverage only: each provider still ages data on its own schedule, found does not mean deliverable, and non-empty values can still be wrong.

Each underlying provider keeps its own re-verification schedule, so a found email can be stale and still needs validation (Talantir). The widely used decay benchmark is 2.1% a month, about 22.5% a year; ZoomInfo cites a 22.5–70% range because fields decay at different rates, and one vendor's weekly re-verification study claims about 67% a year, a single-vendor sample that is not consensus (Merit).

Myth
A waterfall makes data more accurate

Reality: It primarily raises coverage. Accuracy depends on validation and on stopping on validated results (Talantir).

Myth
Failed lookups are always free

Reality: Clay says no-result steps cost nothing, but third-party write-ups report per-attempt charges (Clay Docs, Cleanlist). Test before budgeting.

We treat coverage, freshness, validation and governance as four separate layers, each needing its own control. A waterfall addresses only the first.

How should you decide whether to build a waterfall?

Test your single-provider miss rate by segment first, then choose the control model that matches who will maintain provider order, stop rules and write-back.

The control model is the decision axis: you own order in Clay, an admin owns a native-first lineup in Apollo, and ZoomInfo manages order for you (Clay Docs, Apollo docs, ZoomInfo Pipeline). If one provider already clears roughly 80% on an easy list, stay with it. If misses cluster in specific segments, add providers there and validate before anything reaches the CRM.

Frequently asked questions

Does Apollo have waterfall enrichment?

Yes. Apollo made waterfall enrichment the default for finding emails and phone numbers in December 2025, checking its own data first and then selected third-party sources (Apollo release notes). Apollo reports about 5% more emails, 7% more phones and 45% fewer bounces, with no baseline stated. Comparison pages saying Apollo has no waterfall are outdated.

Is ZoomInfo a true waterfall?

It depends on the definition. Per ZoomInfo, GTM Studio queries its own database first, then fills gaps from third-party vendors in parallel and returns the highest-confidence result, rather than running sequential first-match (ZoomInfo Pipeline). If you define a waterfall as ordered first-match, it is not one; if you define it as multi-provider gap-fill, it is. This is a vendor description.

Are failed lookups free in a waterfall?

It depends on the platform. Clay's FAQ says no-result steps are not charged (Clay Docs), while community threads and third-party write-ups report per-attempt charges (Cleanlist). Run a small test batch and compare consumption to results before budgeting.

Does a waterfall make enrichment data more accurate?

Not by itself. A waterfall mainly raises coverage. Accuracy depends on a validation step and a stop rule that requires a validated result, because non-empty values can still be wrong and each provider's data ages on its own schedule (Talantir).
